Guía de arquitectura

Medusa Analyzer KEOPS

Esta guía explica cómo se construye el dashboard, cómo se descubren los experimentos, cómo se insertan los pasos del workflow en el stack, qué papel juega el state, cómo funcionan Router y Navigator, cómo lanzar Workers y cómo reutilizar el validador genérico sin volver a hardcodear reglas.

Ruta real de arranque

main.py Lanzador mínimo que delega en medusa_analyzer.main.main().
medusa_analyzer/main.py Delegación directa a frontend.app.run().
frontend/app.py Crea MainWindow, el stack principal y el router.
frontend/experiments/__init__.py Descubre experimentos y crea páginas completas de workflow.

Ideas clave

Dashboard Sale de info.json de cada experimento, pasado por discover_experiments() y build_dashboard_catalog().
Workflow Sale de la lista workflow del info.json y se inserta en WorkflowShell.
State Es el diccionario compartido entre todos los steps de un experimento.
Validación Se centraliza en frontend/models/validation.py y se invoca desde widgets concretos.

Secciones

Regla mental útil: el dashboard resuelve qué experimentos existen; el workflow resuelve qué pasos tiene un experimento; el state resuelve cómo se comunican esos pasos.

Cómo tocar el dashboard sin perderse

Estas son las operaciones típicas: añadir una categoría nueva, meter un experimento dentro de una categoría ya existente o dejar una tarjeta visible pero bloqueada.

Añadir una categoría nueva
  • Crea o edita el info.json del experimento.
  • Dentro de category, usa un id nuevo y único.
  • Define title, description y order.
  • No hace falta tocar dashboard.py; build_dashboard_catalog() la detecta sola.
Añadir un experimento dentro de una categoría existente
  • Usa el mismo category.id que ya usan otros experimentos de esa sección.
  • Ajusta el order del experimento para decidir en qué posición sale la tarjeta.
  • Define route único, icon, title y workflow.
Mostrar una tarjeta pero deshabilitada
  • Pon "enabled": false en el info.json.
  • La tarjeta seguirá existiendo, pero no navegará.
  • ExperimentCard cambiará accesibilidad, cursor, tooltip y badge automáticamente.
  • El texto del badge sale de status; si no lo defines, la base pone un fallback.
Objeto Campo relevante Para qué sirve
DashboardCategory id, title, subtitle, order Define la sección del dashboard.
DashboardItem title, subtitle, route, icon_path Describe una tarjeta clicable.
DashboardItem status, accent, enabled Controla el badge, la apariencia y si se puede abrir o no.
DashboardPage.route_requested Señal Qt Es el puente entre el click en una tarjeta y Router.navigate().

Contrato mínimo de un experimento

Los experimentos viven dentro de medusa_analyzer/frontend/experiments/. discover_experiments() recorre cada carpeta y solo acepta aquellas que tengan info.json, defaults.json y un workflow válido.

Qué valida discover_experiments()

  • Que la carpeta no empiece por __.
  • Que exista info.json.
  • Que exista defaults.json.
  • Que el JSON se pueda leer.
  • Que info.json tenga route y una lista workflow no vacía.

Qué define info.json y qué define defaults.json

La separación es deliberada: info.json describe el experimento como módulo navegable; defaults.json contiene la configuración de trabajo que usarán los widgets.

info.json

id Identificador lógico del experimento.
title, subtitle, description Textos visibles en dashboard y workflow.
category Sección del dashboard donde aparecerá la tarjeta.
route Clave que usa el Router para navegar a la página del experimento.
icon Path relativo al icono de la tarjeta.
workflow Lista ordenada de steps con id, title y widget.

defaults.json

Bloques por step Cada widget suele leer su propio bloque: load_data, preprocessing, features, report.
Valores de arranque Extensiones permitidas, filtros, bandas, features y opciones de report.
Fuente de verdad local El widget no debería hardcodear defaults si pueden vivir en este JSON.

Cómo se resuelve un widget desde el info.json

El string del step no se usa solo como nombre. _resolve_widget_class() lo convierte en un import real. Si pones "widget": "eeg_features_widget.EEGFeaturesWidget", el sistema acabará importando medusa_analyzer.frontend.experiments.eeg.widgets.eeg_features_widget. 

{
  "workflow": [
    {
      "id": "features",
      "title": "Features",
      "widget": "eeg_features_widget.EEGFeaturesWidget"
    }
  ]
}

Cómo se inserta el workflow en el stack

create_experiment_page() crea el state, recorre la lista workflow, instancia cada widget y monta una lista de steps. Esa lista se pasa a WorkflowShell, que a su vez mete cada widget en un QStackedWidget interno a través de Navigator.add_page().

1

create_experiment_page()

Crea el state compartido y resuelve cada clase de step.

2

Lista steps

Cada entrada tiene id, title y el objeto widget instanciado.

3

WorkflowShell

Mete esos widgets en el stack, pinta la barra de progreso y controla la navegación.

Router vs Navigator

Hay dos niveles de navegación. Si se mezclan mentalmente, se vuelve difícil entender por qué una cosa cambia la página completa y otra solo cambia el step actual.

Router

Cambia de página global dentro del stack principal de MainWindow.

  • register(route, page)
  • navigate(route)
  • Ejemplos: dashboard, experiment:eeg, converter

Navigator

Cambia de step interno dentro del WorkflowShell de un experimento.

  • add_page(page)
  • go_to(index)
  • next() y back()
  • Ejemplos: Load data → Preprocessing → Features → Final report

Señales y condiciones de avance

WorkflowShell escucha la señal changed si existe, y con eso recalcula si el botón Next debe estar activo. Además, si el widget actual implementa can_continue(), esa función decide si se puede avanzar.

Step EEG Widget Condición actual de can_continue()
Load data EEGLoadDataWidget → hereda LoadDataWidget bool(state["metadata_list"])
Preprocessing EEGPreprocessingWidget Sampling rate resuelta y filtros válidos y tabla de bandas válida.
Features EEGFeaturesWidget → hereda FeaturesWidget No debe haber errores de validación acumulados.
Final report EEGReportWidget → hereda ReportWidget No implementa can_continue(); WorkflowShell deja terminar.
Qué hace changed
Si el widget emite changed, WorkflowShell llama a _refresh_navigation(). Eso actualiza la barra de progreso, el texto de los botones y si Next está habilitado.
Qué hace on_step_activated()
Cuando entras en un step, WorkflowShell llama a on_step_activated() si el widget lo implementa. EEG lo usa para refrescar preprocessing, features y report con el último state.
Cómo añadir un step nuevo a un experimento
  • Crea el archivo del widget dentro de experiments/mi_experimento/widgets/.
  • Añade la entrada correspondiente en info.json → workflow.
  • Si necesita defaults, crea su bloque en defaults.json.
  • Si debe bloquear el avance, implementa can_continue().
  • Si necesita refrescar al entrar, implementa on_step_activated().

El state es la pieza central

Todos los experimentos usan una variable compartida llamada state. No es una copia por step; es el mismo diccionario mutable que se crea en create_experiment_page() y se pasa a todos los widgets. Ahí se va guardando la interacción del usuario y es el mecanismo principal de comunicación entre pasos.

Memoria compartida Se crea una vez por experimento Todos los steps leen y escriben
Regla práctica: si un step necesita que el siguiente sepa algo, lo correcto es escribirlo en state. Si lo dejas solo en variables internas del widget, el resto del workflow no lo verá.

Quién escribe qué dentro del state

Esta es la forma útil de entenderlo: no como un JSON abstracto, sino como responsabilidades por step.

Load data

Escribe loader_results, metadata_list y loaded_file_paths. Además deja el estado preparado para que los siguientes steps trabajen con las claves actuales.

Preprocessing

Escribe state["preprocessing"] con CAR, notch, bandpass, tabla de bandas, selected_frequency_bands y broadband.

Features

Actualiza selected_features, feature_params y eeg_feature_state.

Report

No suele persistir nada nuevo; recompone visualmente lo que ya existe en el state.

Qué hereda EEG y qué compone EEG

Aquí conviene ser preciso. En EEG sí hay widgets específicos que heredan de genéricos, pero no todos siguen exactamente el mismo patrón. Load data, Features y Report heredan base genérica. Preprocessing es un widget específico que reutiliza subwidgets genéricos por composición.

EEGLoadDataWidget

Vive en eeg_load_data_widget.py y hereda de LoadDataWidget. Lo específico es el loader=load_edf_file y los textos visibles.

EEGFeaturesWidget

Hereda de FeaturesWidget. Añade dependencias PSD, validación de features EEG y la lógica de bandas para band power relativo/absoluto.

EEGReportWidget

Hereda de ReportWidget. Sobrescribe la forma de resumir preprocessing y features del experimento EEG.

EEGPreprocessingWidget

No hereda de un PreprocessingWidget genérico. Compone FilterControls, FilterPreviewPlot y EEGFrequencyBandsTable. Ese detalle importa si alguien quiere generalizar preprocessing en el futuro.

Puntos funcionales importantes del EEG actual

Esto resume cómo está organizado el EEG después del refactor de validación y bandas.

Bandas de frecuencia
EEGFrequencyBandsTable extiende EditableTable y encapsula la tabla de bandas EEG. La validación vive en validate_eeg_frequency_bands(). El paso de preprocessing recalcula sus límites con Nyquist y con el bandpass activo.
Preprocessing y broadband efectiva
EEGPreprocessingWidget construye una banda broadband efectiva para que el resto del flujo trabaje con un marco de frecuencia consistente. Esa banda también se escribe en state["preprocessing"].
Features dependientes del preprocessing
EEGFeaturesWidget lee state["preprocessing"] para resolver bandas efectivas, forzar la dependencia de PSD y decidir si relative_band_power usa bandas del preprocessing o una tabla custom.
Report final
EEGReportWidget no recalcula nada. Resume metadata, preprocessing y features a partir del state ya consolidado.

Cómo usar un worker en este proyecto

La infraestructura está en frontend/workers/worker.py y frontend/workers/task_runner.py. El patrón actual es sencillo: envuelves una función costosa en un Worker, conectas señales y lanzas el trabajo con TaskRunner.start(worker).

Receta

  1. Escribe una función pesada que pueda ejecutarse fuera del hilo de UI.
  2. Crea worker = Worker(mi_funcion, *args).
  3. Conecta progress, result, error y finished.
  4. Lanza self.runner.start(worker).

Detalle importante

Worker.run() inyecta automáticamente progress_callback en kwargs. La función costosa puede llamar a ese callback para notificar progreso sin tocar directamente la UI.

Ejemplo real: LoadDataWidget

El uso más claro está en widgets/load_data.py. Ese widget selecciona ficheros, crea un Worker con _load_files, escucha el progreso y actualiza el estado cuando llega el resultado. 

worker = Worker(_load_files, self.loader, paths)
worker.signals.progress.connect(self.overlay.progress.setValue)
worker.signals.result.connect(self._loaded)
worker.signals.error.connect(self._failed)
worker.signals.finished.connect(self._finished_loading)
self.runner.start(worker)
Señal Emisor Uso típico
progress WorkerSignals Actualizar barras de progreso u overlays.
result WorkerSignals Recibir el resultado calculado y persistirlo en state.
error WorkerSignals Mostrar el fallo en UI sin bloquear la app.
finished WorkerSignals Limpiar overlays, reactivar botones y sacar el worker del set activo.

El modelo genérico de validación

La capa genérica vive en frontend/models/validation.py. La idea es que el widget específico diga qué regla quiere aplicar, no que vuelva a programar esa regla. El objeto Validation expone validate(), validate_errors() y validate_many().

validate() validate_errors() validate_many()
Ejemplo simple: un valor numérico tiene que ser menor que otro valor dado. 
validator = Validation()
errors = validator.validate_many(
    value,
    [
        "finite_number",
        ("less_than", {"maximum": max_value, "suffix": " Hz"})
    ],
    label="High cut"
)

Reglas reutilizables que ya existen

Antes de inventar una validación nueva, conviene revisar si una regla genérica ya la cubre.

Clave Qué comprueba Casos típicos
required_text Texto obligatorio no vacío. Nombres de banda, labels, ids visibles.
no_whitespace Que no haya espacios. Nombres de banda EEG.
finite_number Que el valor sea numérico y finito. Frecuencias, ripple, attenuation, thresholds.
integer Que sea entero. Órdenes de filtro, escalas, contadores.
greater_than, greater_or_equal Límites inferiores. > 0, orden mínimo, frecuencia mínima.
less_than, less_or_equal Límites superiores. Nyquist, fs / 2, máximos de UI.
one_of Que el valor pertenezca a un conjunto de opciones. Diseños IIR, ventanas FIR, combos.
minimum_length Que haya suficientes elementos. Seleccionar al menos una banda o una feature.
pattern Que el texto siga un formato concreto. [1, 3, 5] en multiscale LZ.
custom Delegar en una función específica. Reglas compuestas de un workflow concreto.

Dónde se usa ahora mismo en EEG

Checklist: añadir un experimento nuevo

Esta es la secuencia útil si alguien quiere extender KEOPS con un experimento nuevo sin tocar más de lo necesario.

1. Carpeta

  1. Crea frontend/experiments/mi_experimento/.
  2. Añade __init__.py, icon.png, info.json, defaults.json y widgets/.

2. Metadata de catálogo

  1. Define title, subtitle, description.
  2. Define category, status, accent, enabled, order.
  3. Define route único.

3. Workflow

  1. Rellena workflow con la lista ordenada de steps.
  2. Apunta cada widget a una clase real de widgets/.

4. Defaults

  1. Crea los bloques de configuración que leerá cada widget.
  2. Evita defaults hardcodeados si pueden vivir en defaults.json.

5. State

  1. Decide qué claves nuevas vas a escribir en state.
  2. Mantén nombres coherentes y evita duplicar la misma información en varios sitios.

6. Validación y avance

  1. Si un step debe bloquear Next, implementa can_continue().
  2. Usa Validation para reglas comunes y custom para reglas compuestas.
